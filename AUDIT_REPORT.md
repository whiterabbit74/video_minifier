# Отчет по аудиту кода VideoSzhimaka

В ходе проверки кода были выявлены следующие проблемы, классифицированные по степени критичности.

## 🔴 Критические (Critical)

### 1. Состояние гонки (Race Conditions) в `FFmpegService`
**Файл:** `VideoSzhimaka/Services/FFmpegService.swift`

Класс `FFmpegService` помечен как `@unchecked Sendable`, но не обеспечивает должной потокобезопасности для своих мутабельных свойств `currentProcess` и `currentProgressTask`.
- **Проблема:** Метод `performVideoCompression` (выполняющийся асинхронно) и `cancelCurrentOperation` (выполняющийся на `processQueue`) могут одновременно обращаться к `currentProcess`.
- **Риск:** Неопределенное поведение при отмене операции, возможность падения приложения (crash) или утечки процесса FFmpeg, если он не будет корректно завершен.

### 2. Утечка ресурсов/потоков в `FFmpegService`
**Файл:** `VideoSzhimaka/Services/FFmpegService.swift`

В методе `monitorProgress` цикл `while` проверяет `currentProcess != nil`.
- **Проблема:** Если `cancelCurrentOperation` выставляет `currentProcess = nil`, цикл завершается. Однако, если `process.run()` выбросит исключение *до* назначения `process.terminationHandler` или во время инициализации, переменная `currentProcess` может остаться в неопределенном состоянии или не быть очищенной, если логика обработки ошибок не сработает идеально.
- **Блокировка потоков:** Использование `usleep` в `extractVideoMetadata` блокирует поток. Хотя это происходит в background queue, это неэффективно.

## 🟠 Серьезные (Major)

### 3. Некорректный расчет загрузки CPU
**Файл:** `VideoSzhimaka/Services/PerformanceMonitorService.swift`

Метод `getCPUUsage` рассчитывает среднюю загрузку CPU **с момента запуска системы**, а не текущую мгновенную загрузку.
- **Проблема:** Возвращаемое значение будет меняться крайне медленно и не отражает реальной нагрузки, создаваемой приложением прямо сейчас. Для корректного расчета необходимо сохранять предыдущее состояние счетчиков (`host_cpu_load_info`) и вычислять дельту.

### 4. Конфликт настроек кодека (Hardware Acceleration + CRF)
**Файл:** `VideoSzhimaka/Models/CompressionSettings.swift` / `FFmpegService.swift`

В `CompressionSettings.swift` параметр `-crf` добавляется в список аргументов даже при использовании аппаратного ускорения (`-c:v h264_videotoolbox` / `hevc_videotoolbox`).
- **Проблема:** Энкодеры VideoToolbox обычно не поддерживают флаг `-crf`. Они используют `-q:v` (качество 0-100) или настройки битрейта (`-b:v`). Передача `-crf` может привести к ошибке запуска FFmpeg или игнорированию параметра качества, что приведет к непредсказуемому размеру/качеству выходного файла.

### 5. Потеря идентификации файлов при перезапуске (Persistence)
**Файл:** `VideoSzhimaka/Models/VideoFile.swift`

Свойство `let id = UUID()` инициализируется новым значением при каждом создании объекта.
- **Проблема:** Так как `id` не входит в `CodingKeys` и не декодируется, при сохранении и последующей загрузке (если функционал сохранения очереди будет реализован) все файлы получат новые ID. Это сломает любую логику, которая ссылается на файлы по ID (например, выбор пользователя или статус обработки).

## 🟡 Минорныe (Minor)

### 6. Ненадежный парсинг вывода FFmpeg
**Файл:** `VideoSzhimaka/Services/FFmpegService.swift`

Метод `parseFFmpegOutput` использует регулярные выражения для разбора текстового вывода FFmpeg (fallback, если `ffprobe` не сработал).
- **Проблема:** Формат вывода FFmpeg может меняться между версиями или зависеть от входного файла. Это делает парсинг хрупким. Рекомендуется всегда использовать JSON-вывод `ffprobe`.

### 7. Жестко закодированные пути к FFmpeg
**Файл:** `VideoSzhimaka/Services/FFmpegService.swift`

Сервис ищет FFmpeg только по фиксированному списку путей (`/opt/homebrew/bin/ffmpeg` и т.д.).
- **Проблема:** Если у пользователя FFmpeg установлен в нестандартном месте, приложение не сможет его найти, даже если он есть в `PATH`.

### 8. Singleton-путаница в AppDelegate
**Файл:** `VideoSzhimaka/VideoSzhimakaApp.swift`

Существует два экземпляра `AppDelegate`: один создается через `@NSApplicationDelegateAdaptor`, второй — статический `AppDelegate.shared`.
- **Проблема:** Методы меню (например, "Показать окно") обращаются к `AppDelegate.shared`, который может не иметь актуального состояния или ссылок на окна, управляемые основным циклом SwiftUI.

### 9. Инвалидация индексов в MainViewModel
**Файл:** `VideoSzhimaka/ViewModels/MainViewModel.swift`

В асинхронном методе `compressFileAtIndex` происходит обращение к массиву `videoFiles` через индекс или поиск по ID.
- **Риск:** Если файл был удален пользователем во время обработки (хотя UI пытается это предотвратить), поиск по индексу может вернуть неверный файл (если индексы сместились) или привести к ошибке, если логика защиты не сработает. Использование `firstIndex(where:)` внутри асинхронного блока — более безопасный подход, но требует тщательной проверки `nil`.

## Рекомендации

1.  **Thread Safety:** Использовать `NSLock` или перевести `FFmpegService` полностью на акторы (Actors) для защиты состояния.
2.  **CPU Monitor:** Переписать `getCPUUsage` для расчета разницы между замерами.
3.  **VideoToolbox:** Добавить специфичную логику для VideoToolbox аргументов (использовать `-q:v` вместо `-crf`).
4.  **Codable:** Добавить `id` в `CodingKeys` для `VideoFile` и сделать его переменной (`var`) или константой с возможностью инициализации при декодировании.
5.  **AppDelegate:** Объединить логику в единый класс-делегат или использовать Environment-объекты для управления состоянием окон.
